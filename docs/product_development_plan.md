## Rules for every step

1. The step is explained to the owner before work starts, in plain language, saying what is built and why.
2. Files are written as files the owner can open and read, not hidden in commands.
3. Tests are written with the step, not afterwards.
4. This plan and `architecture.md` are updated at the end of the step: what was built, what was learned, what changed.
5. Assumptions listed in `architecture.md` section 13 are proved or corrected by a test, and the document is updated.

## Current repository state (honest)

- The repository holds the package under `src/taskline`, its tests (287 pass, also with deprecation warnings treated as errors), the schema `0001_schema.sql`, and the command line for migrate, worker, reaper, queues, runs, show, cancel, retry and requeue. Scheduling is not built.
- Taskline's own containers (`compose.yaml`): Valkey on port 6380, and a standalone Postgres on port 5435 behind the `standalone` profile.
- Taskline lives in its own repository, `anilvenugopal/taskline`. Its admin UI is the separate Taskline UI project, which builds against the contract in `docs/public_contract.md`.
